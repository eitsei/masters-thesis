# Adaptive-RAG: Learning to Adapt Retrieval-Augmented Large Language Models through Question Complexity
**Authors:** Soyeong Jeong, Jinheon Baek, Sukmin Cho, Sung Ju Hwang, Jong C. Park | **Year:** 2024
**Category:** Routing

### 📝 Abstract & Relevance Summary
Retrieval-Augmented Large Language Models (LLMs) enhance response accuracy by integrating external databases, but typical systems use a "one-size-fits-all" approach. They either handle simple queries with unnecessary retrieval/computational overhead or fail to address complex multi-hop queries accurately. To solve this, the authors propose Adaptive-RAG, an adaptive QA framework that dynamically selects the most appropriate strategy for an incoming query, ranging from "no retrieval" (direct generation) to "single-step retrieval" and up to "multi-step iterative retrieval" based on query complexity. This complexity is assessed dynamically using a classifier—a smaller language model (such as T5-Large) trained on automatically collected labels representing actual query difficulty. This framework balances operational efficiency (by bypassing retrieval and minimizing steps for simple questions) and output quality (by reserving expensive multi-hop reasoning for complex questions).

### 🚀 Efficiency & Cost Metrics (RQ1 & RQ2)
- **Latency Impact:** Bypassing retrieval for straightforward questions reduces the latency per query to **0.35 seconds** (direct generation), compared to **3.08 seconds** for single-step retrieval and **27.18 seconds** for multi-step iterative RAG. Adaptive-RAG reduces relative elapsed time per query by **56%** compared to the multi-step approach (from 3.33 to 1.46 relative time).
- **Cost & Token Usage:** By dynamically routing queries, Adaptive-RAG decreases the average number of retrieval-and-generation steps from **2.81 steps** (for the multi-step baseline) to **1.03 steps** per query. This leads to a **~63% reduction** in LLM query/token consumption relative to the multi-step baseline, since 8.6% of queries are routed to "no retrieval" and 53.33% to "single-step retrieval," with only 38.07% requiring "multi-step retrieval."
- **Throughput:** Reducing steps and execution time significantly boosts system throughput, enabling RAG pipelines to handle more concurrent requests.

### 🏆 Quality & Accuracy Metrics (RQ3)
- **Quality Metrics:** Evaluated using Exact Match (EM), F1 Score, and Accuracy (Acc). F1 score measures token-level overlap; EM measures exact string match; Accuracy measures if the correct answer is contained in the output.
- **Benchmark Data:** Evaluated on a mix of single-hop (SQuAD v1.1, Natural Questions, TriviaQA) and multi-hop (MuSiQue, HotpotQA, 2WikiMultiHopQA) open-domain QA datasets.
- **Judge Setup:** Standard dataset ground truth matching is used rather than an LLM judge.

### ⚖️ The Trade-off Analysis
- **Efficiency-Quality Equilibrium:** Adaptive-RAG achieves an F1 score of **50.91%** and EM of **37.97%** on GPT-3.5, which is virtually identical to the F1 score of the multi-step approach (50.87% F1 / 38.13% EM) but with a **56% latency reduction** and **63% token step reduction**.
- **Pareto Frontier & Combinations:** Demonstrates a highly optimized Pareto frontier. By using an Oracle classifier, F1 can rise to **62.80%** with a step count of **0.50**, indicating that improved classifiers can further push the efficiency-quality boundary.
- **Chunking/Routing Strategy:** Routes queries into three complexity classes:
  - *Class A (No Retrieval)*: Direct LLM generation.
  - *Class B (One-Step)*: A single BM25 retrieval step of $k$ documents followed by generation.
  - *Class C (Multi-Step)*: Iterative reasoning and retrieval using the IRCoT pipeline.
- **Enterprise Suitability:** Highly suitable for enterprise search and customer support, where a large percentage of queries are simple (e.g., entity lookups) and can be answered immediately, while only a subset of queries require expensive and slow multi-hop retrieval.

### 📊 Methodology & Bias Note
- **Evaluation Framework:** Standard open-source evaluation metrics on unified QA benchmarks.
- **Bias Detection:** Since the classifier is trained on dataset labels generated by actual model outcomes (silver labels showing which models succeeded on which questions) combined with inductive biases in the datasets, it is less prone to LLM self-preference bias. However, if the base LLM (e.g., GPT-3.5) changes, the classifier's routing thresholds might require retraining.

### 🔍 Technical Implementation
- **Portability:** Fully portable to Java/Spring AI. The classifier is a standard sequence classification model (like T5 or BERT) which can be deployed as an ONNX model or called via a local Python microservice. The routing logic is simply an `if-else` block in the Java orchestration layer routing the user's query to one of three Spring AI chains.
- **Key References:**
  1. *IRCoT*: Trivedi, H., et al. (2023). Interleaving Retrieval with Chain-of-Thought Reasoning for Knowledge-Intensive Multi-Step Questions.
  2. *Mallen et al.* (2023). When Not to Retrieve: K-NN Search for Robust Large Language Models.
  3. *Self-RAG*: Asai, A., et al. (2024). Learning to Retrieve, Generate, and Critique through Self-Reflection.

### 💡 Key Takeaway for Thesis
- Adaptive-RAG shows that classifying query complexity via a small classifier (T5-Large) allows systems to route simple queries away from retrieval and multi-step reasoning, capturing 99% of the quality of full multi-step RAG while cutting latency and token costs by over 55%.
